# Notes for coding agents

- This is a dependency-free installable web app (PWA). Edit files in `src/`, then run `python3 build.py`; commit both `src/` and the generated `index.html` and `sw.js`.
- Hosting: Cloudflare Pages straight from `main`, no build step. Server code lives in `functions/` (Pages Functions); `_routes.json` limits them to `/api/*`.
- AI: the app calls `/api/ai` (see `makeApiSample` in `src/app.js`). Inside Claude (the published prototype artifact) it uses `window.claude` instead; keep both paths working.
- Data lives in `localStorage` (`S`, key `repwerk-proto-v2`). `src/cloud.js` adds Supabase login (email code) and sync without an SDK: the whole `S` is one JSON row in `public.user_state` (see `supabase/setup.sql`), newest `S.at` wins, `save()` schedules a push. Config comes from `/api/health` (Cloudflare env `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`). Send the publishable key only in the `apikey` header, never as `Authorization: Bearer`. Keep `S` serialisable.
- UI language is German, with English via `src/i18n.js` (DOM translation). Any new German UI string needs an English entry there, except in `src/smart.js`, `src/cloud.js` and `src/barcode.js`, which write both languages inline with `L(de, en)`.
- `src/smart.js` is the smart coach (the USP): day targets for training and rest days (`dayTargets`), the weekly check-in (`checkinCalc`) and load suggestions (`suggestLoad`). Use `dayTargets(k)` or `baseTargets()` instead of `S.targets` in views; `S.targets` is only the formula result before check-in adjustments.
- Community goes through `CB` (in `src/cloud.js`): `claudeCB` inside Claude, `supaCB` (tables `public.profiles`, `public.posts`) in the web app; `syncCommunity()` switches it with the login state. Never call `DB` directly for community features.
- `src/barcode.js`: barcode scanning (native `BarcodeDetector` → ZXing WASM ponyfill from jsDelivr → own EAN-13/EAN-8 decoder `decodeImageData`, which works offline) and Open Food Facts via `/api/food` (`functions/api/food.js`, custom User-Agent and edge cache) with a direct fallback. Scanned and self-made foods live in `S.myFoods` and show up first in the food search.
- Workout photos (`src/media.js`): workouts store only refs `photos: [{ id, url? }]`; the JPEG lives in IndexedDB (`repwerk-media`) and, when signed in, in the public Storage bucket `workout-photos` at `<uid>/<id>.jpg`. Render with `photoStrip()`; `<img data-ph>` is filled from IndexedDB automatically. Never put image data URLs into `S`.
- AI limits are enforced on the server: with Supabase configured, `/api/ai` requires the user's access token and calls `public.use_ai(kind)` (kinds `scan`, `text`, `coach`, `mealplan`). Client-side limits are only for UX.
- Pro: `public.entitlements` is written only by `functions/api/stripe-webhook.js` (Supabase secret key in the `apikey` header). The app reads it via `refreshPro()`; when `payOn()` the demo unlock is disabled. Checkout and portal: `functions/api/checkout.js`, `portal.js`.
- `supabase/setup.sql` must stay idempotent (safe to run again). It can be tested against a local PostgreSQL with a small auth/storage scaffold.
- Legal (`legal/`, `src/legalui.js`, `functions/api/cancel.js`): static pages read provider data from `legal/anbieter.js`. Keep the footer links (`legalFooter()`) on every view; the cancellation page `legal/kuendigen.html` must stay reachable without login and contain only the § 312k fields and the "jetzt kündigen" button. Health data may only go to the server or the AI after `S.consent.health` is set (`needConsent()`, `consentSheet()`); checkout requires `terms` and `earlyStart` from the order summary.
- No third-party requests for fonts or other assets: fonts are self-hosted in `fonts/`. The only external script is the ZXing ponyfill from jsDelivr (mentioned in the privacy policy); update `legal/datenschutz.html` when adding any external service.
- The Expo version of the app is parked on branch `expo-app`.
